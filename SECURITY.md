# Security Policy

Security, privacy, and responsible disclosure are important to this project.

If you discover a potential security vulnerability affecting the repository, its code, dependencies, or associated workflows, please report it privately using the process below.

---

## Supported Versions

Security fixes are generally applied to the current version of the project maintained on the `main` branch.

| Version | Supported |
| --- | --- |
| Current `main` branch | Yes |
| Older releases or revisions | Generally no |

Older releases may receive security-related updates only when explicitly stated.

---

## Reporting a Vulnerability

Please **do not open a public GitHub issue** for a suspected security vulnerability.

Instead, report the issue privately to the project maintainer:

**Email:** [mdnaimhassansaykat@gmail.com](mailto:mdnaimhassansaykat@gmail.com)

When possible, include:

- A clear description of the vulnerability and its potential impact.
- The affected file, component, dependency, or workflow.
- Steps required to reproduce or verify the issue.
- Relevant version, commit, operating system, or environment information.
- Minimal logs, code snippets, or proof-of-concept information necessary to understand the issue.
- Any suggested mitigation, if known.

Please do not include passwords, authentication tokens, private keys, personal data, patient information, or other sensitive information in a report.

---

## What to Report as a Security Issue

Examples of appropriate security reports include:

- Vulnerabilities that could enable arbitrary or unintended code execution.
- Unsafe handling of untrusted files or inputs.
- Exposure of credentials, secrets, or sensitive configuration.
- Vulnerable dependency or workflow configurations that create a meaningful security risk.
- Repository or automation behavior that could compromise the integrity of the software or development process.

Ordinary software bugs, documentation errors, model-performance concerns, reproducibility questions, and feature requests should normally be reported through the repository's public issue tracker rather than through the security-reporting process.

Concerns involving research integrity, methodological errors, or incorrect reported results may also be raised through the project's normal issue or maintainer-contact channels unless confidential handling is necessary.

---

## Disclosure and Response Process

After receiving a security report, the maintainer will make a reasonable effort to:

1. Acknowledge receipt of the report.
2. Review and reproduce the reported issue where possible.
3. Assess its potential severity and impact.
4. Develop an appropriate fix, mitigation, or documentation update when necessary.
5. Coordinate disclosure of confirmed vulnerabilities when appropriate.

The time required to investigate and resolve an issue may vary depending on its complexity, severity, and the availability of a suitable mitigation.

Reporters are asked to allow reasonable time for investigation and remediation before publicly disclosing a vulnerability.

---

## Responsible Disclosure

When investigating or reporting a vulnerability, please:

- Act in good faith and avoid unnecessary disruption.
- Access only information necessary to demonstrate the issue.
- Do not attempt to obtain, modify, or disclose data belonging to others.
- Do not publicly disclose an unresolved vulnerability before reasonable remediation efforts have taken place.
- Avoid publishing exploit code that could unnecessarily expose users to harm before an appropriate fix or mitigation is available.

Responsible security research conducted in good faith is appreciated.

---

## Medical and Research Context

This repository is an academic research and reproducibility project involving machine-learning methods for dermoscopic skin-lesion classification.

Security reports should concern vulnerabilities in the software, dependencies, repository configuration, or associated technical workflows. Questions about model predictions, clinical validity, diagnostic performance, or appropriate medical use are not, by themselves, software-security vulnerabilities.

The software and research outputs should not be treated as a substitute for professional medical judgment or clinical diagnosis.
